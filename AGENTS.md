# Общие требования: Angular + C#

## Стек и структура
- Frontend — Angular и TypeScript, backend — C# и ASP.NET Core Web API.
- Использовать поддерживаемые стабильные версии; фиксировать версии SDK и зависимостей, хранить lock-файлы в Git.
- Разделять исходники: `frontend/`, `backend/`; тесты хранить рядом с кодом или в отдельных проектах тестов.
- Организовывать код по функциональности. Не вводить дополнительные слои, библиотеки и сервисы без необходимости.

## Принципы программирования

- Соблюдать SOLID: разделять ответственность, сохранять контракты при расширении и замене реализаций, делать интерфейсы узкими и управлять зависимостями через явные контракты.
- KISS: выбирать простое и понятное решение, избегать лишних уровней абстракции.
- DRY: не дублировать бизнес-правила; объединять код с общей причиной изменения, а не только с похожим синтаксисом.
- YAGNI: реализовывать текущие требования, не добавлять функциональность и гибкость «на будущее».
- Соблюдать разделение ответственности и инкапсуляцию; предпочитать композицию наследованию.
- Писать небольшие связные функции с понятными именами и явными зависимостями; минимизировать скрытые побочные эффекты.
- Применять принципы соразмерно задаче: каждая абстракция должна решать конкретную проблему.

## C# и API
- Включать nullable reference types; соблюдать единый стиль именования и форматирования.
- Обработчики запросов держать небольшими; бизнес-правила не размещать в контроллерах.
- Использовать встроенный DI; для операций ввода-вывода — `async/await` и передачу `CancellationToken`.
- Определять явные DTO и контракт OpenAPI; не возвращать сущности БД напрямую.
- Проверять входные данные на сервере; возвращать корректные HTTP-коды и ошибки в формате Problem Details.
- Для списков с потенциально большим объемом данных использовать пагинацию.

## Данные и безопасность
- Секреты хранить вне Git: в переменных окружения или хранилище секретов. Конфигурация frontend считается публичной.
- Проверять аутентификацию и права на backend для защищенных операций; проверки в интерфейсе не заменяют серверные.
- Использовать HTTPS и ограничивать CORS нужными origin; не записывать секреты и персональные данные в логи.
- Использовать параметризованные запросы; изменения схемы БД оформлять миграциями. Разрушительные изменения данных требуют согласования.

## Качество и изменения
- Соблюдать существующие соглашения проекта; менять только необходимое для задачи.
- Покрывать значимую бизнес-логику unit-тестами, взаимодействие API и БД — интеграционными; исправления ошибок сопровождать регрессионными тестами.
- Перед завершением запускать доступные сборку, линтер и относящиеся к изменению тесты; явно сообщать, что не запускалось.
- В CI проверять сборку frontend/backend и тесты; не добавлять зависимости с известными уязвимостями без согласования.

## Коммиты
- В `docs/TODO.md` каждый пункт с чекбоксом считается отдельной задачей. Если запрос охватывает несколько пунктов или целый раздел, для каждого выполненного пункта нужен свой коммит.
- После выполнения пункта запустить относящиеся к нему проверки, просмотреть diff и создать коммит до перехода к следующему пункту. Например, каркас backend, миграция SQLite и Swagger UI оформляются отдельными коммитами, если они указаны отдельными пунктами TODO.
- Для задач вне TODO действует то же правило «одна задача — один коммит». Включать в коммит только изменения текущей задачи.
- Писать сообщения коммитов на английском языке по Conventional Commits: `<type>[optional scope][!]: <description>`.
- Выбирать тип по характеру изменений, например `feat`, `fix`, `docs`, `refactor`, `test`, `build`, `ci` или `chore`.
- Пример: `docs: define commit requirements`.
