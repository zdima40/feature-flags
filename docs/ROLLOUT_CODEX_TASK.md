# Rollout — техническое задание для Codex

## Роль агента

Ты — AI coding agent, отвечающий за реализацию небольшого, законченного fullstack pet-проекта **Rollout**. Основной приоритет — качественный frontend на Angular. Backend на C# должен быть минимальным, но реальным: UI работает с HTTP API и сохраняет данные в SQLite.

**Принцип работы:** сначала изучай текущее состояние репозитория, затем предлагай короткий план и реализуй задачу небольшими, проверяемыми шагами. Не усложняй архитектуру без необходимости. Если репозиторий пустой, начни с создания каркаса.

## 1. Цель проекта

Создать минималистичную панель управления **feature flags** для веб-приложений.

Продукт должен позволять:

- Просматривать все флаги, искать и фильтровать их.
- Создавать и редактировать флаги.
- Управлять состоянием флагов отдельно для окружений **Development**, **Staging**, **Production**.
- Устанавливать процент постепенного включения (**rollout**, от 0 до 100%).
- Просматривать историю изменений конкретного флага.

Проект предназначен для демонстрации Angular, взаимодействия с ASP.NET Core API, тестирования, архитектурной дисциплины и прозрачного процесса AI-assisted разработки.

### Страницы

**1. `/flags` — список флагов**

- Таблица/список: название, уникальный ключ, описание (кратко), окружение, статус, rollout %, время последнего изменения.
- Переключатель окружения (Development / Staging / Production).
- Поиск по имени и ключу.
- Фильтр по состоянию (все / включены / выключены).
- Серверная пагинация с отображением общего количества результатов и доступными с клавиатуры элементами перехода между страницами. При изменении поиска, фильтра или окружения возвращаться на первую страницу.
- Быстрое переключение `enabled` с обновлением через API и обработкой ошибок.
- Кнопка «Создать флаг».
- Навигация к редактированию и истории.

**2. `/flags/new` и `/flags/:id/edit` — создание/редактирование**

- Поля `name`, `key`, `description`.
- Поле `key` уникальное, формат: латинские буквы, цифры, дефисы и подчёркивания; после создания не редактируется.
- Выбор окружения.
- `enabled` и `rolloutPercentage` (0–100).
- При создании форма задаёт начальные значения для выбранного окружения. Остальные окружения инициализируются со значениями `enabled=false` и `rolloutPercentage=0`.
- Валидация до отправки и отображение ошибок сервера.
- Сохранение, отмена, индикация незаписанных изменений по возможности без усложнения.

**3. `/flags/:id/history` — история изменений**

- Список событий от новых к старым: дата и время, поле, предыдущее и новое значение, актор.
- Событие `created` отображать как «Флаг создан».
- Серверная пагинация истории с отображением общего количества событий.
- Понятное пустое состояние, если история не содержит событий.

## 4. Модель данных

Предпочтительная простая структура:

```text
FeatureFlag
- Id: Guid
- Key: string (unique)
- Name: string
- Description: string?
- CreatedAtUtc: DateTime
- UpdatedAtUtc: DateTime

FlagEnvironmentSettings
- Id: Guid
- FeatureFlagId: Guid
- Environment: enum/string (Development | Staging | Production)
- Enabled: bool
- RolloutPercentage: int (0..100)
- UpdatedAtUtc: DateTime
- unique(FeatureFlagId, Environment)

FlagAuditEvent
- Id: Guid
- FeatureFlagId: Guid
- Environment: string? (null для общих полей)
- Field: string
- OldValue: string?
- NewValue: string?
- Actor: string
- ChangedAtUtc: DateTime
```

Для демо без авторизации указывай фиксированного актора `demo-user`. Не пытайся реализовать настоящую аутентификацию.

**Семантика:** `enabled` — разрешает использование флага в окружении; `rolloutPercentage` — настройка доли пользователей для будущего внедрения. **В MVP не требуется** SDK для вычисления пользовательских бакетов, оценка флага по userId или runtime-распределение трафика. Не изображай настройку процента как реально работающий механизм маршрутизации пользователей.

## 5. HTTP API

Минимальные маршруты:

```http
GET   /api/flags?environment=Development&search=&enabled=&page=1&pageSize=20
GET   /api/flags/{id}
POST  /api/flags
PATCH /api/flags/{id}
GET   /api/flags/{id}/history?page=1&pageSize=20
```

`POST /api/flags` принимает начальные настройки выбранного окружения. Флаг, настройки всех трёх окружений и одно событие создания сохранять вместе в одной транзакции. Для события создания использовать `Field=created`, `Environment=null`, `OldValue=null`, а в `NewValue` записывать ключ флага.

`PATCH /api/flags/{id}` обновляет общие поля флага и настройки одного окружения. Если передан `enabled` или `rolloutPercentage`, параметр `environment` в теле запроса обязателен. UI использует этот маршрут также для быстрого переключения `enabled` в списке.

Пропущенное поле сохраняет прежнее значение. Явное `"description": null` очищает описание. `null` в поле `name`, `enabled`, `rolloutPercentage` или `environment` возвращает `400` в формате Problem Details. Запрос без фактических изменений завершается успешно и сохраняет прежние даты обновления и историю.

Контракт запросов и ответов задокументируй в `README.md` или `docs/api.md`.

Для списка флагов и истории использовать единый формат ответа `{ items, totalCount, page, pageSize }`. Нумерация страниц начинается с 1; значения по умолчанию: `page=1`, `pageSize=20`; допустимый `pageSize` — от 1 до 100. Некорректные параметры возвращают `400` в формате Problem Details, страница за пределами результатов — пустой `items` с корректным `totalCount`.

Поиск и фильтрацию выполнять до подсчета общего количества и пагинации. Флаги сортировать по уникальному `key` по возрастанию, историю — по `ChangedAtUtc` по убыванию с дополнительной сортировкой по `Id` для одинаковых дат. Подсчет и выборку страницы выполнять в БД, не загружать весь список в память.

Обязательные требования к API:

- Серверная валидация имени, ключа, окружения и диапазона rollout 0–100.
- Ключ флага после создания неизменяем; попытку изменить его через API отклонять с `400` в формате Problem Details.
- Уникальность ключа без учёта регистра латинских букв должна обеспечиваться в SQLite. Сохранять регистр исходного ключа для отображения. Если уже есть `New-Checkout`, создание `new-checkout` возвращает `409 Conflict`.
- `404` для отсутствующего флага.
- Ошибки возвращать в формате Problem Details; для ошибок валидации — `400` с понятными сообщениями и привязкой к полям, где применимо.
- Хранение в SQLite, инициализация схемы через миграции EF Core.
- При обновлении сохранять изменения и события аудита в одной транзакции. Создавать по одному событию на каждое фактически изменённое поле.
- Даты в UTC, отображение времени в интерфейсе по локали браузера.
- CORS только для локальной разработки (или прокси Angular), без открытой production-конфигурации по умолчанию.

## 7. Тестирование и готовность

Минимальные проверки:

1. Frontend собирается без ошибок.
2. Backend собирается и стартует с SQLite.
3. Создание флага сохраняется в БД; после перезапуска данные не пропадают.
4. Поиск, фильтры и пагинация списка и истории работают; общее количество учитывает фильтры, изменение поиска, фильтра или окружения сбрасывает страницу списка.
5. Для каждого окружения независимо сохраняются `enabled` и rollout.
6. Быстрое переключение обновляет UI и API; ошибка запроса отображается, интерфейс не остается в ложном состоянии.
7. Валидация ключа и диапазона rollout работает на frontend и backend.
8. История содержит корректные изменения и не плодит событий при no-op обновлениях.
9. UI корректен на узком экране, доступен с клавиатуры.
10. Есть автоматические проверки, описанные ниже; все обязательные проверки выполняются в CI.

### Автоматические тесты

- **Vitest + Angular TestBed:** валидация форм, запрет изменения ключа существующего флага, состояния загрузки/пустого результата/ошибки и поведение быстрого переключения при неуспешном сохранении. API-сервис проверять через `HttpTestingController`: параметры окружения, поиска, фильтра и пагинации, тела запросов и обработку ошибок. Unit-тесты не должны обращаться к реальному API.
- **xUnit:** критичные бизнес-правила, включая валидацию rollout, начальные настройки окружений, событие создания и аудит фактически изменённых полей.
- **Microsoft.AspNetCore.Mvc.Testing + SQLite:** создание и чтение флага с настройками всех окружений и одним событием `created`, конфликт ключей с разным регистром (`409`), отсутствующий флаг (`404`), серверная валидация (`400` и Problem Details), неизменяемость ключа, независимость настроек окружений и поиск/фильтрация/пагинация. Для `PATCH` проверить сохранение пропущенных полей, очистку описания через `null`, запись `false` и `0` и появление событий аудита с прежними и новыми значениями. При повторном запросе с теми же значениями даты обновления и история должны сохраняться.
- Интеграционные тесты должны использовать отдельную SQLite, изолированную от данных разработки, применять миграции EF Core и освобождать ресурсы после выполнения. Не подменять SQLite провайдером EF Core InMemory. Проверку сохранности данных после перезапуска выполнять на временном файле SQLite с повторным запуском приложения и чтением сохраненного флага.
- **Playwright:** основной сценарий против реального backend и SQLite: создать флаг → настроить окружение → изменить статус и rollout → открыть историю → проверить значения. Дополнительно проверить поиск/фильтры, переход между страницами и сохранение настроек при смене окружения. Для сценария ошибки быстрого переключения допустимо перехватить запрос и вернуть ошибку, проверив сообщение и корректное состояние UI.
- E2E должны автоматически запускать frontend и backend, ожидать их готовности, использовать отдельную тестовую БД и независимые данные. Тесты должны быть повторяемыми, без зависимости от порядка выполнения, фиксированных задержек и локальных данных разработчика.
- В Playwright использовать локаторы по роли и доступному имени, встроенные ожидания и assertions. Основной сценарий запускать в Chromium; отдельно проверять список, форму и историю на desktop и узком экране, например шириной 390 px, без потери доступа к действиям.
- **@axe-core/playwright:** сканировать список, форму и историю после загрузки, а также открытый диалог, если он используется. Проверять автоматически обнаруживаемые нарушения WCAG 2.2 A/AA; исправлять обнаруженные проблемы, не отключать правила ради прохождения тестов. Дополнительно вручную проверить навигацию клавишами Tab/Shift+Tab, видимый фокус, активацию элементов клавиатурой и возврат фокуса после закрытия диалогов. Автоматический скан не заменяет ручную проверку.

### Команды и CI

- В `frontend/package.json` определить команды `build`, `lint`, `format:check`, `test:ci` и `e2e`. `test:ci` запускает Vitest без watch-режима, `e2e` — настроенный `ng e2e` без интерактивного выбора инструмента. Проверка форматирования не должна изменять файлы.
- В CI устанавливать npm-зависимости через `npm ci`, .NET-зависимости восстанавливать в locked mode. Устанавливать браузер Chromium и его системные зависимости для Playwright.
- Выполнять `npm run build`, `npm run lint`, `npm run format:check`, `npm run test:ci`, сборку backend, `dotnet test` и `npm run e2e`. Ошибка любого обязательного шага должна завершать проверку неуспешно.
- При падении E2E сохранять Playwright report, trace и скриншоты как артефакты CI. Отчеты и временные тестовые БД не включать в Git.
- В README описать установку зависимостей и браузера, команды всех проверок, запуск тестового окружения, используемые URL/порты и расположение отчетов. Зафиксировать ручные проверки и их фактический результат в итоговом отчете.

По завершении запускай доступные тесты/сборки и **явно сообщай**, что прошло, что не прошло и какие команды использовал. Не утверждай, что всё проверено, если проверки не выполнялись.

## 8. Как работать над задачей

1. Изучи репозиторий, существующие инструкции и файлы. Если существует `AGENTS.md`, следуй ему.
2. Сформулируй краткий план из этапов с проверяемым результатом.
3. Предложи рациональные команды и структуру проекта; при отсутствии принципиальных неопределённостей продолжай реализацию.
4. Работай по этапам: **каркас → backend/API → список → форма → история → тесты/CI/документация**.
5. После каждого этапа проверяй сборку/тесты, анализируй diff и исправляй регрессии.
6. Если обнаружен существенный архитектурный выбор или требуется выход за рамки MVP, **сначала объясни альтернативы и причину**, не добавляй расширение автоматически.
7. Если твое решение отличается от явно заданных требований, не подменяй требования молча: изложи расхождение и запроси решение.
8. Не переписывай несвязанный код ради косметических изменений.
9. После каждой выполненной задачи создавай отдельный коммит: одна задача = один коммит. Сообщения — на английском языке по Conventional Commits, как требует `AGENTS.md`. Не фальсифицируй историю или сведения об участии AI.
10. В конце предоставь итог: выполненные функции, структуру, команды запуска/проверки, известные ограничения.

## 9. Прозрачность AI-разработки

Создай `docs/ai-development.md` с разделами:

- Используемый агент и фактическая модель (заполнять **только достоверными данными**).
- Этапы разработки с ссылками на реальные коммиты/PR, если они существуют.
- Какие задачи выполнял агент, какие решения и проверки оставались за человеком.
- Примеры замечаний на ревью и внесённых исправлений (если были).

**Не придумывай** названия моделей, PR, коммитов, ревью или результаты проверок. Git-история должна отражать реальный ход разработки, а не быть специально инсценированной.

## 10. За пределами MVP

Не реализуй без отдельного запроса:

- регистрацию, логин, роли и права доступа;
- интеграцию с внешними OAuth/SSO;
- SDK для frontend/backend приложений, которые читают feature flags;
- real-time обновления через WebSocket;
- сегментацию пользователей и алгоритм раскатки по userId;
- микросервисы, брокеры сообщений, Kubernetes;
- аналитику, платёжную систему, многопользовательский SaaS.

## 11. Критерий завершения

Готовый результат — небольшой, хорошо выглядящий fullstack репозиторий, который можно клонировать, запустить локально, пройти сценарий **создать флаг → настроить окружение → изменить статус/rollout → увидеть запись в истории** и проверить через автоматические тесты. Главная цель — показать **качество Angular frontend и управляемый процесс разработки с AI-агентом**, а не количество функций.
